一句话总结：OpenClaw 把"派单"做成了独立组件（Gateway），让多个常驻 agent 各司其职；Hermes 把"派单"和"干活"压缩进同一个 LLM 的推理循环里，没有上层调度器。

2一句话区分

OpenClaw

🏢 公司模型

Gateway = HR + 调度中心

  • HR 管着一群全职员工（常驻 agent）
  • 派单按规则/配置/RPC 指令
  • 每个员工自己有大脑（LLM），但不决定"谁来干"
Hermes

👤 个体户模型

一个万能快递员

  • 自己接单、自己派单、自己干
  • 派单依据 = LLM 当场推理（tool_call 决策）
  • 忙不过来才临时叫零工（sub-agent 即用即走）
关键认知翻转：两者都有推理（都用 LLM），区别不是"有没有推理"，而是"调度决策发生在哪一层"——上层架构里，还是 LLM 推理里。

3OpenClaw 架构

3.1 Gateway 是什么

Gateway 是 OpenClaw 的中枢，本质是一个常驻的 WebSocket RPC 服务（默认监听 18789），对外提供一组管理 agent 生命周期与会话路由的方法：

RPC 方法作用
sessions.spawn启动新会话
sessions.list列出当前会话
agents.create创建新 agent 实例
agents.list列出已注册 agent
channels.status查询接入通道状态
cron.add注册定时任务
关键认知：Gateway 自己不一定带 LLM——它的"智能"在于路由规则与生命周期管理。真正的推理在它管理的每个 agent 内部完成。

3.2 工作流程

┌─────────────────────────────────────────────────────────┐ │ 外部入口（IM / API / Cron） │ └──────────────────────────┬──────────────────────────────┘ │ 任务请求 ▼ ┌─────────────────────────────────────────────────────────┐ │ Gateway (RPC :18789) │ │ · 调度规则 / 路由策略 / 生命周期管理 │ └──┬─────────────┬─────────────┬─────────────┬────────────┘ │ │ │ │ ▼ ▼ ▼ ▼ ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐ │Agent1│ │Agent2│ │Agent3│ │Agent4│ │ LLM │ │ LLM │ │ LLM │ │ LLM │ │ A │ │ B │ │ C │ │ D │ └──────┘ └──────┘ └──────┘ └──────┘ 常驻 常驻 常驻 常驻 （不同人设/不同模型/不同技能集）

Gateway 把请求路由到合适的 agent，再由该 agent 调用自己的 LLM 完成任务并回传。

4Hermes 架构

4.1 单 Agent 模型

Hermes 部署的是一个 agent 进程，对外暴露两套接口：

🔌
API 接口

默认端口 8642，OpenAI 兼容协议，可被任何 OpenAI 客户端直接调用。

🖥
WebUI

默认端口 9119，提供浏览器端的对话与配置界面。

⚠️ 易混点 — "hermes gateway" 命令：Hermes 自带一个 gateway 子命令，但它不是任务调度器，而是 IM / API 接入层（Telegram / Discord 等消息源 → 主 agent 的转接桥）。请不要把它和 OpenClaw 的 Gateway 概念混淆。

4.2 工作流程

┌─────────────────────────────────────────────────────────┐ │ 外部入口（HTTP API :8642 / WebUI :9119 / IM） │ └──────────────────────────┬──────────────────────────────┘ │ ▼ ┌─────────────────────────────────────────────────────────┐ │ Hermes Main Agent │ │ ┌──────────────────────────────────────────────────┐ │ │ │ LLM 推理循环（自驱动） │ │ │ │ · 思考 → 决策 → tool_call → 观察 → 再思考 │ │ │ └────┬───────────┬───────────┬──────────────┬─────┘ │ │ │ │ │ │ │ │ ▼ ▼ ▼ ▼ │ │ [skills] [tools] [memory] [sub-agent] │ │ ↑ 临时 spawn │ └─────────────────────────────────────────────────────────┘

没有上层调度器——LLM 在推理循环里自己判断要不要调技能、调工具、查记忆，或者临时spawn 一个子 agent 来分担任务。子 agent 用完即销毁，不常驻。

5两层 Gateway 视角 ⭐

💡 这是理解两个项目最关键的一节。"gateway" 这个词在两个项目里指的不是同一件事——拆开看，OpenClaw 其实是两层 gateway 叠在一起，Hermes 只有其中一层。

5.1 先把 "gateway" 拆成两件事

层干啥关键词
① 接入层 Ingress让外部消息进得来（Telegram / Discord / HTTP / WebUI / Cron → 内部）协议转换
② 调度层 Dispatch决定"这个任务给谁干"（→ 哪个 agent / 哪个 skill）任务路由

套到两个项目上：

接入层调度层
OpenClaw✅ 有（多通道入口）✅ 有（Gateway RPC :18789）
Hermes✅ 有（hermes gateway 命令）❌ 无（LLM 推理自己当调度）
结论：OpenClaw 确实是"两层 gateway"，Hermes 只有"一层 gateway + 一个会自己派单的 LLM"。

5.4 根本原因：进程数量决定了要几层 gateway

问题答案
OpenClaw 是不是也有 Hermes 那种 gateway？是，就是图里的 ① 接入层
OpenClaw 的"独家"在哪？在 ① 之上又加了 ② 调度层 Gateway
Hermes 为啥不需要 ②？它把 ② 的活塞进了 LLM 的推理循环里，省掉一层独立组件
那 OpenClaw 为啥不也这么干？它要管多个常驻 agent 进程——LLM 自己派单只能在自己进程内派，跨进程派单必须有个外部调度者
一句话锁死：两层 vs 一层的根本原因 = 进程数量。跨进程必须有外部调度（OpenClaw 的 ② 调度层 Gateway）；单进程 LLM 自己就能调（Hermes 把调度内嵌在推理里）。

6关键差异

6.1 调度层级：架构调度 vs 推理调度

OpenClaw · 架构级

调度抽到了 agent 之外。Gateway 先决定"这个任务给谁干"，再让那个 agent 用 LLM 干。"调度"和"推理"是两层、两个组件。

Hermes · 推理级

调度内嵌在 LLM 推理里。"找谁干"的决策由 agent 自己的 LLM 通过 tool_call 触发。"调度"和"推理"在同一个组件内合一。

6.2 Agent 生命周期：常驻员工 vs 临时零工

维度OpenClawHermes
启动方式Gateway 显式 agents.create主 agent 推理时按需 spawn
存在周期常驻进程，直至 kill用完即销毁
管理者Gateway 统一管控（spawn/list/kill）无外部管理者，主 agent 自主创建
类比HR 雇全职员工临时叫零工

6.3 推理位置：分散 vs 集中

OpenClaw："推理"分散在每个 agent 内部，Gateway 只负责"调度不推理"。
Hermes："调度"和"推理"全在主 agent 的同一个 LLM 里，子 agent 是它推理过程中的"延伸臂"。

8常见误解辨析

❌
误解 1

"OpenClaw 是调度器，Hermes 是推理引擎"

不准确。两者都有推理（都用 LLM），差别是：OpenClaw 把调度抽到了 agent 之外的 Gateway 层，Hermes 把调度内嵌在了 agent 的 LLM 推理里。

❌
误解 2

"OpenClaw 是 LLM 路由网关（外包多个 LLM API）"

不准确。OpenClaw 不是单纯调外部 LLM 服务，而是多 agent 编排平台——下挂的是它自己管理的常驻 agent 进程，每个 agent 自带 LLM。

❌
误解 3

"Hermes 的 gateway 子命令 = OpenClaw 的 Gateway"

完全不同。Hermes 的 gateway 只是 IM/API 接入层（消息源转接），不做任务调度；OpenClaw 的 Gateway 是核心调度中枢。

❌
误解 4

"Hermes 没有多 agent 能力"

能 spawn 子 agent，但临时性的——由主 agent 在推理过程中按需创建，用完即销毁，没有常驻多 agent 编队的概念。

9适用场景

🏢
选 OpenClaw 的场景
  • 多角色稳定分工：客服 / 研报 / 运维各一个 agent，互不打扰
  • 多通道接入：IM、API、定时任务统一经 Gateway 路由
  • 显式可控调度：希望路由规则可配置、可审计
  • 异构模型组合：不同 agent 用不同模型 / 不同 prompt
多 Agent 编队 规则可审计 企业级
⚡
选 Hermes 的场景
  • 一个聪明大脑搞定一切：依赖 LLM 当场判断怎么干
  • OpenAI 兼容接入：现有 OpenAI 客户端可直接接入
  • 轻量级单机部署：不需要常驻多 agent 编队
  • 灵活技能扩展：纵向加 skill/tool 比横向加 agent 更顺手
单 Agent 自驱动 OpenAI 兼容 轻量级

10一句话点睛

🎯 以后看到这两个名字就这么想
OpenClaw = 一个 Gateway + 一群常驻 agent（每个自带 LLM），Gateway 派单。
Hermes = 一个 agent + 一个 LLM，需要帮手时自己临时 spawn sub-agent。
本质区别 = "调度"放在哪一层：架构层（OpenClaw 的 Gateway）还是推理层（Hermes 的 LLM 循环）。两边都有大脑，区别只在有没有一个凌驾在所有 agent 之上的"调度大脑"。
类比锁死 = OpenClaw = 公司（HR + 一群全职员工）·Hermes = 个体户（一个人干，忙了才叫零工）。
