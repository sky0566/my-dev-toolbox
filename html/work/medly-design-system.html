Overview

Building a unified design language for healthcare

Medly Health is a healthcare SaaS company with 5 product lines: patient portal, provider dashboard, pharmacy management, telehealth platform, and admin console. Each product had been designed independently by different teams over 3 years, resulting in wildly inconsistent user experiences — different button styles, color schemes, typography, and interaction patterns across products.

I led the creation of a comprehensive design system from the ground up, establishing a single source of truth that unified all 5 products under one coherent visual language. The system includes foundational tokens, a component library, layout patterns, and governance documentation.

Background

The fragmentation problem

When I joined Medly, a UI audit across all 5 products revealed staggering inconsistency:

  • 14 different button styles — varying in border-radius, padding, font-weight, and hover states across products.
  • 6 different primary color values — ranging from #1a73e8 to #0066cc, all intended to represent the same "Medly Blue."
  • 3 different type scales — one product used rem-based scaling, another used px, and a third used a custom modular scale.
  • No shared iconography — some products used Material Icons, others used Font Awesome, and one used custom SVGs.

This fragmentation caused real business pain: users who switched between products (e.g., a pharmacy technician using both the pharmacy management and admin console) reported confusion and increased error rates. Support tickets citing "interface confusion" averaged 45 per month.

Process

Phase 1 — Audit & Foundation

I started by conducting a comprehensive interface inventory across all 5 products, cataloging every unique UI element. I organized findings in a spreadsheet with screenshots, CSS values, and usage frequency.

Design Tokens

I established the foundational layer: a set of design tokens covering color, typography, spacing, elevation, border radius, and motion. Tokens were structured in three tiers:

  • Global tokens: Raw values (e.g., blue-500: #6366f1)
  • Alias tokens: Semantic mappings (e.g., color-primary: blue-500)
  • Component tokens: Scoped to components (e.g., button-primary-bg: color-primary)

This three-tier structure allows theming — the telehealth product uses a calming teal palette while the admin console uses a more neutral slate, all by swapping alias tokens without changing components.

Key Decision: I chose a 4px spatial grid (4, 8, 12, 16, 24, 32, 48, 64) based on analysis of the most common spacing values already in use. This minimized the visual disruption during migration while establishing a consistent rhythm.

Figma Structure

I organized the Figma library using a clear naming convention: [Category] / [Component] / [Variant] / [State]. Components use auto-layout and variant properties extensively, allowing consumers to swap between sizes, themes, and states without detaching instances.

Process

Phase 3 — Documentation & Adoption

A design system is only valuable if teams actually use it. I invested heavily in documentation and adoption strategy.

Zeroheight Documentation Site

I built a living documentation site on Zeroheight that includes for every component:

  • Usage guidelines with do/don't examples
  • Anatomy diagram showing each sub-element
  • Accessibility specifications (ARIA roles, keyboard interactions)
  • Code snippets from Storybook (synced automatically)
  • Design rationale explaining why certain decisions were made

Adoption Strategy

Rather than mandating adoption, I took a collaborative approach:

  1. Pilot with one product: Started with the patient portal (smallest surface area), migrated it fully, and documented before/after metrics.
  2. Office hours: Held weekly 30-minute "design system office hours" where any designer or engineer could ask questions or request new components.
  3. Contribution model: Established a process for teams to propose new components: need → review → design → build → document → publish.

Adoption Result: Within 6 months, all 5 products had migrated to the design system. Designer onboarding time for new hires dropped from 3 weeks to 1 week. UI inconsistency bugs in the backlog decreased by 60%.

Delivery

Results & ongoing iteration

Before Design System

14 button styles, 6 color values for "primary," 3 type scales, no shared components. Average time to design a new feature: 2 weeks. UI inconsistency tickets: 45/month.

After Design System

1 unified component library (120+ components), 1 token system with product-level theming, 1 documentation site. Average time to design a new feature: 1.2 weeks. UI inconsistency tickets: 18/month.

The design system is now a living product with its own roadmap. I continue to maintain it, adding new components as product needs evolve and iterating on existing ones based on designer and developer feedback.

Reflection

Lessons learned

  1. Start with tokens, not components: Getting the foundational values right (color, spacing, type) made component design dramatically faster and more consistent.
  2. Adoption is a people problem: The technical quality of the system mattered less than making it easy and rewarding for teams to adopt. Office hours and the pilot approach were critical.
  3. Document the "why": Designers are more likely to follow guidelines when they understand the reasoning behind them. "Use 8px spacing between form fields" is less compelling than explaining the cognitive grouping principle behind it.
